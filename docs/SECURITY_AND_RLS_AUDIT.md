# تدقيق الأمان وSupabase

تاريخ التدقيق: 16 نوفمبر 2026

## الحكم

**FAIL للإنتاج حاليًا.** أُنجز الإصلاح البرمجي والترحيل محليًا، لكن لم يُطبّق ملف SQL على قاعدة الإنتاج ولم تُنفّذ مصفوفة اختبار بحسابين حقيقيين. لا يجوز وصف ثغرة النسخ الاحتياطي بأنها مغلقة قبل هاتين الخطوتين.

## الخطر الأصلي

- كان حد الملكية يعتمد على بريد يرسله العميل بدل هوية مصادق عليها من الخادم.
- كان من الممكن أن تسمح سياسات أو صلاحيات عامة غير منضبطة بقراءة أو تعديل نسخ لا يملكها المستخدم.
- كان مسار التحدي العالمي يحتوي على تحديث احتياطي غير ذري ويمكن أن يفقد زيادات متزامنة.
- كانت النسخة الاحتياطية أوسع من الحد الأدنى اللازم وقد تشمل بيانات حساسة أو داخلية.

## الإصلاح المحلي

- صار تسجيل Google يُستبدل بجلسة Supabase Auth فعلية، ويُستخدم `auth.uid()` كحد ملكية وحيد، ويرفض العميل ID token أو access token الفارغ.
- قُسم SQL إلى معاملتين: مرحلة احتواء تفرض RLS وتلغي صلاحيات `PUBLIC` و`anon` و`authenticated` والسياسات القديمة قبل أي ترحيل، ثم مرحلة ملكية ودوال.
- أُضيف `owner_id` وسياسات RLS للقراءة والإدراج والتحديث والحذف الخاصة بصاحب الصف فقط، وقُيدت القراءة العامة للتحدي بالصف `tasbih_challenge` وحده.
- دالة استرداد النسخ القديمة لا تقبل بريدًا من العميل؛ تتحقق من بريد مؤكد وهوية Google داخل `auth.users` و`auth.identities`. تطالب بأحدث صف مطابق فقط، تمحو بريده القديم، وتترك التكرارات للمراجعة بدل حذفها أو دمجها تلقائيًا.
- أُلغيت الكتابة المباشرة للتحدي العام، وأصبح التحديث ذريًا ومحدودًا بمعدل عبر RPC لا يقبل مجرد جلسة مصادق عليها بل يشترط هوية Google مؤكدة.
- النسخ الاحتياطي يستخدم قائمة مفاتيح مسموحة، يستبعد البريد والموقع والجلسات والبيانات الداخلية، ويرفض حمولة أكبر من 512KB أو أنواعًا غير متوقعة.
- الاستعادة تتحقق من جميع العناصر قبل أول كتابة، فلا تترك حالة جزئية عند وجود عنصر تالف متأخر.
- يحفظ العميل زيادات التحدي المعلقة محليًا، يرسلها على دفعات لا تتجاوز 100 وبحد أقصى ثلاث دفعات للدورة، ويعيد المحاولة بعد عودة المصادقة أو الشبكة.
- أُضيف حذف النسخة السحابية للمستخدم الحالي من داخل التطبيق ثم تسجيل الخروج.

## ما لم يُنفذ على الإنتاج

1. مراجعة نسخة احتياطية مشفرة لقاعدة البيانات ثم تطبيق `supabase/migrations/202611140001_secure_cloud_data.sql` داخل نافذة صيانة.
2. ضبط `GOOGLE_WEB_CLIENT_ID` المتوافق مع إعداد Google وSupabase. البناء الحالي يفشل مغلقًا عند غيابه ولا يفعّل النسخ السحابي.
3. تنفيذ الاختبارات التالية دون عرض أو نسخ محتوى مستخدم حقيقي:
   - حساب A يستطيع CRUD لصفه فقط.
   - حساب B لا يستطيع SELECT أو UPDATE أو DELETE لصف A حتى عند معرفة المعرّف.
   - دور `anon` لا يستطيع الوصول إلى `app_backups`.
   - استرداد صف قديم ينجح فقط لصاحب بريد Google المؤكد.
   - الزيادة 0 أو أكبر من 100، أو تجاوز 300 في الدقيقة، تُرفض.
   - التزامن لا يفقد الزيادات المقبولة.
4. مراجعة الصفوف القديمة ذات البريد المكرر أو `owner_id = null` قبل فرض خطة ترحيل نهائية؛ SQL المحلي يتعمد ترك المكرر دون حذف.

## حذف الحساب

الحذف الحالي يمحو بيانات النسخ الاحتياطية فقط، ولا يحذف مستخدم Supabase Auth. وبما أن التطبيق ينشئ هوية تطبيق عند تسجيل الدخول، يلزم مسار خادمي موثوق لحذف حساب Auth وبياناته، وزر داخل التطبيق، ورابط HTTPS خارجي منشور. لذلك يبقى هذا البند **FAIL** حتى التنفيذ والتحقق.

## اختبارات محلية

- أربعة اختبارات وحدة لحدود النسخة الاحتياطية: قائمة السماح، استبعاد البيانات الخاصة، رفض الحجم أو النوع غير الصالح، ومنع الاستعادة الجزئية.
- التحليل الساكن واختبارات Flutter نجحا وفق `docs/TEST_RESULTS.md`.
- تمت مراجعة SQL ساكنًا فقط؛ لم يُنفذ على قاعدة اختبار أو محلل PostgreSQL فعلي. هذه الاختبارات لا تثبت إعداد RLS الفعلي على الإنتاج.
